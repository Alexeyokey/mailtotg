# Сводки почтовых ящиков в Telegram

Сервис для личного использования: читает один или два ящика по IMAP/TLS, сохраняет новые письма и отправляет уведомления и сводки в один указанный личный чат Telegram. Сводки работают по расписанию и по команде `/summary`. `/status` показывает состояние подключений и обеих очередей доставки.

Реализованы MIME/HTML → текст, изоляция ошибок ящиков, UID-дедупликация, сохранение курсоров и очереди в SQLite, возобновление доставки по частям после перезапуска. Письма читаются через `BODY.PEEK` в режиме readonly. Вложения и внешние изображения не открываются. Максимальный размер скачанного письма и текста ограничен; обрезка указывается в содержимом.

## Запуск на компьютере

Нужны Python 3.11+ и macOS/Linux. Выполняйте команды из папки проекта.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/python -m pip install --no-deps .
cp config.example.toml config.toml
cp .env.example .env
chmod 600 .env config.toml
```

В `config.toml` заполните один или два `[[accounts]]`: адрес IMAP, email, id и название переменной с паролем. Чтобы начать с одного ящика, удалите второй блок. В `.env` сохраните пароль IMAP, токен отдельного бота и id вашего личного чата. Gmail/Mail.ru/Яндекс обычно требуют **пароли приложений**; корпоративный сервер может поддерживать обычный пароль по своей инструкции. Не отправляйте секреты в переписку и не добавляйте их в Git.

`id` привязан к серверу, адресу и папке. При замене ящика задайте новый `id`; повторное использование старого id блокируется, чтобы не спутать UID двух разных ящиков. Старые уже подготовленные сводки остаются в очереди до доставки.

| Почта | IMAP/TLS | Настройка доступа |
|---|---|---|
| Gmail | `imap.gmail.com:993` | 2FA и пароль приложения, если он доступен для аккаунта |
| Mail.ru | `imap.mail.ru:993` | Пароль внешнего приложения |
| Яндекс | `imap.yandex.ru:993`; для сервера за рубежом можно попробовать `imap.ya.ru` | Включить IMAP и доступ с паролями приложений; создать пароль приложения |

Эта версия использует IMAP LOGIN с паролем. Для Gmail/организационных аккаунтов, запрещающих пароли приложений, потребуется добавить OAuth; автоматическое получение/обновление OAuth-токенов здесь не реализовано. Источники: [Gmail IMAP](https://developers.google.com/workspace/gmail/imap/imap-smtp), [Google app passwords](https://support.google.com/accounts/answer/185833?hl=en), [Mail.ru](https://help.mail.ru/mail/login/mailer/), [Яндекс](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others).

### Telegram

1. Создайте отдельного бота через [BotFather](https://t.me/BotFather), внесите токен в `.env`.
2. Откройте своего бота в Telegram и отправьте `/start`.
3. Выполните `.venv/bin/mail-summary-bot chat-id`: он читает обновления и выводит id личных чатов, не отправляя сообщений и не обращаясь к почте. Укажите свой id в `TELEGRAM_CHAT_ID`.
4. Проверьте конфигурацию и запустите сервис:

```sh
.venv/bin/mail-summary-bot check
.venv/bin/mail-summary-bot run
```

`check` проверяет конфигурацию и наличие переменных, **не проверяет авторизацию или сетевую доступность**. Для первой реальной проверки запустите `run`, отправьте новое письмо в каждый ящик и `/summary` боту. В `/status` каждый настроенный ящик должен иметь `ok`; проверьте содержимое доставленной сводки. Только этот тест подтверждает работу всей цепочки.

Используйте отдельный токен: одновременно работающий другой poller или установленный webhook мешает `getUpdates`. Сервис не удаляет webhook автоматически. Команды принимаются только из настроенного личного чата. [Telegram Bot API](https://core.telegram.org/bots/api#getupdates).

### Расписание и первая загрузка

По умолчанию — сводка в 09:00 `Europe/Moscow`; проверка почты каждую минуту. Только новые письма после первого запуска: `bootstrap = "new"`. Непрочитанные письма, уже лежавшие в ящике, автоматически не импортируются. Если нужны последние сутки, **до первого запуска** выставьте `bootstrap = "lookback"`, `lookback_days = 1`. Смена настройки не сбрасывает уже сохранённый курсор.

Для уведомлений по мере обнаружения установите `notify_new_mail = true` в `[service]`. После каждого опроса новые письма ставятся в отдельную очередь Telegram: отправитель, тема, дата и короткая выдержка без AI. Отправка начинается после обнаружения, до ожидания новых команд Telegram; при большом числе писем действует ограничение частоты отправки. Задержка обнаружения зависит от `poll_seconds` и доступности серверов. Уведомления не исключают письма из утренней сводки или `/summary`. Уже сохранённые до включения уведомлений письма массово не пересылаются. На новом экземпляре с `bootstrap = "lookback"` импортируемый период считается новыми записями и также даст уведомления.

При смене сервером UIDVALIDITY повторно загружается недавний период: как минимум `lookback_days`, с расширением на время с последнего успешного опроса. Повторы с одинаковым Message-ID и содержимым отсекаются внутри ящика. В сводке или `/status` показывается уведомление о восстановлении; письма без стабильного Message-ID либо с изменённым содержимым могут повториться. Перенос сервером старых писем за пределами этого периода автоматически не восстанавливается.

Для ежечасной сводки: `schedule = "interval"`, `digest_interval_minutes = 60`. Для запросов вручную: `schedule = "manual"`. `/summary` работает в любом режиме, выдаёт ещё не доставленные письма. При отсутствии новых писем автоматический запуск ничего не отправляет. Большой накопившийся набор делится на партии по `max_digest_messages`; все партии уходят в рамках одного запроса сводки.

```sh
# Однократный опрос и доставка новых писем; реально отправляет сообщения.
.venv/bin/mail-summary-bot once
# Демонстрация на встроенных фиктивных письмах; без сети и учётных данных.
.venv/bin/mail-summary-bot demo
```

## AI-сводки

По умолчанию `summary.mode = "extractive"`: **короткие выдержки, без AI**. Этот режим позволяет проверить почту и Telegram без ключа модели.

Для содержательной AI-сводки выберите один из вариантов:

- `mode = "openai"`: укажите `SUMMARY_API_KEY`, `SUMMARY_MODEL` с доступной вам API-моделью; endpoint по умолчанию `https://api.openai.com/v1`. Тексты писем отправляются API-провайдеру. Используется Responses API с `store=false`, без инструментов; этот флаг отключает сохранение Responses state и сам по себе не означает отсутствие любых журналов у провайдера. [Официальная OpenAI documentation](https://developers.openai.com/api/docs/guides/migrate-to-responses), [data controls](https://developers.openai.com/api/docs/guides/your-data).
- `mode = "ollama"`: установите и запустите Ollama на собственном сервере, задайте имя установленной модели в `SUMMARY_MODEL` и адрес сервера в `SUMMARY_API_URL` (обычно `http://127.0.0.1:11434`). Если бот в Docker, `127.0.0.1` относится к контейнеру, не к хосту; укажите достижимый адрес Ollama. Эта версия не устанавливает модель автоматически.

Модель получает текст писем как данные, с инструкцией игнорировать команды внутри них и выделять только явно указанные действия/сроки. У модели нет доступа к почтовым паролям, токену Telegram или инструментам. Письма в запросе нумеруются и содержат id ящика. При ошибке AI письма сохраняются до повторной обработки; скрытого перехода на выдержки нет. Обрезка входа помечается. AI может ошибаться — исходные тема и отправитель сохраняют контекст для проверки.

## Независимость от VPN на компьютере

**Рекомендуемый вариант — весь сервис на отдельном VPS**, включая чтение почты, построение сводок и доставку Telegram. Тогда VPN и выключение ноутбука не влияют на сервис. Если используется Ollama, она также должна быть доступна с VPS независимо от ноутбука. Сам VPS должен иметь доступ к IMAP/TLS 993, Telegram HTTPS 443 и выбранному AI endpoint. Доступность проверяется с сервера.

В проекте есть Docker Compose для запуска на VPS:

```sh
# config.toml и .env заранее заполнены на VPS; не копируйте .venv с Mac.
docker compose up -d --build
docker compose logs --tail=100 bot
```

Постоянные данные находятся в Docker volume `state`; не используйте `docker compose down -v`, если требуется сохранить курсоры и очередь. `docker compose stop` останавливает сервис и сохраняет состояние. Для изменения настроек `.env` выполните `docker compose up -d --force-recreate`. Для локального варианта виртуальное окружение `.venv` настроено отдельно.

`bot-egress` — отдельная сеть Docker для организации контейнеров. **Она не создаёт отдельный физический выход в интернет и не гарантирует обход VPN хоста.** Docker Desktop на Mac использует сеть компьютера; системный tunnel/kill switch может затронуть контейнер. [Docker Desktop networking](https://docs.docker.com/desktop/features/networking/networking-how-tos/), [Docker bridge](https://docs.docker.com/engine/network/drivers/bridge/).

Есть явные отдельные настройки `TELEGRAM_PROXY_URL` и `SUMMARY_PROXY_URL`, например `socks5://user:password@host:1080` или HTTP-прокси. Клиенты HTTPX используют `trust_env=False` и не наследуют `HTTP_PROXY`/`HTTPS_PROXY`. Это отделяет настройки каналов, но **маршруты и блокировки системного VPN остаются действующими**. IMAP идёт напрямую по TCP/TLS и этими HTTP-прокси не проксируется. Для строго независимого локального запуска нужны настройки обхода конкретного VPN, отдельный интерфейс/роутер или Linux namespace с собственным uplink. Без названия VPN и топологии сети такой обход нельзя подтвердить.

Альтернатива Compose — Linux systemd: шаблон `deploy/mail-summary-bot.service` рассчитан на `/opt/mail-summary-bot` и отдельного пользователя `mailbot`. Конфигурация — `/etc/mail-summary-bot/config.toml`, секреты — `/etc/mail-summary-bot/credentials.env` с правами 600 и владельцем root. Systemd читает секреты до перехода к пользователю сервиса. Каталог `/etc/mail-summary-bot` должен иметь права 750 и группу mailbot, конфиг — 640 с той же группой. В конфиге укажите `database = "/var/lib/mail-summary-bot/state.sqlite3"`; systemd создаёт закрытый каталог состояния. Не запускайте одновременно Compose и systemd с одним Telegram-токеном.

После обновления исходников переустановите пакет в виртуальное окружение сервиса (`/opt/mail-summary-bot/.venv/bin/python -m pip install --no-deps /opt/mail-summary-bot`) и перезапустите systemd. Entry point `mail-summary-bot` использует установленный пакет; одной замены файлов исходников недостаточно.

## Состояние и проверка

SQLite содержит текст писем, сводки и служебные курсоры. Каталог создаётся с правами 700, база и lock — 600; база не зашифрована. После доставки записи удаляются по `retention_days` (по умолчанию 30); недоставленные записи не удаляются автоматически. Логи не включают тексты писем, пароли, токены, полные URL Telegram или ответы авторизации.

Доставка — с повторными попытками. Уведомление сохраняется атомарно вместе с письмом и курсором IMAP; ошибка Telegram не теряет письмо. Успешно подтверждённые части уведомлений и сводок повторно не отправляются после обычного перезапуска. Если Telegram принял сообщение, но соединение оборвалось до получения ответа, или процесс завершился до записи подтверждения в SQLite, возможно повторное сообщение: Bot API не предоставляет idempotency key для `sendMessage`. Поэтому абсолютную доставку ровно один раз эта версия не обещает.

```sh
.venv/bin/python -m unittest discover -s tests -v
```

Тесты используют фиктивные письма/IMAP и HTTP mock transport. Отдельно проверяются ошибки одного ящика, MIME, readonly/PEEK, UID и смена UIDVALIDITY, очередь и восстановление по частям, авторизация команд, ошибки API и расписание. Настоящие почтовые ящики, модель, Telegram, сборка Docker и влияние VPN требуют отдельной проверки после настройки.

## Сбор почты без Telegram

Если Telegram или AI ещё не настроены, команда `mail-summary-bot collect` запускает постоянный сбор писем в ту же SQLite-базу. Нужен только пароль IMAP; токен бота и ключ модели не требуются. Этот режим не отправляет сообщения и не создаёт сводки. Перед запуском `run` остановите collector: блокировка базы защищает от двух одновременных процессов.
